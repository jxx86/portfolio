1. 项目背景与问题定义

1.1 业务背景

高校学生在校期间存在大量闲置物品流转需求，集中在几个典型时间节点：开学季（购置教材、宿舍用品）、毕业季（批量处置带不走的物品）、学期中（数码产品迭代、教材换代）。

目前校园二手交易的现实形态：

现有渠道 具体问题
微信群 / QQ 群 信息刷屏即消失，无检索能力；陌生人直接加好友，隐私暴露
校园贴吧 / 表白墙 图文分离，无结构化商品信息（价格、成色、实拍图）
综合二手平台（闲鱼等） 面向全国，供需双方不在同一校区，交易依赖快递，丧失校园场景"当面交易"的核心优势
线下跳蚤市场 一年仅 1~2 次，时间窗口极短，覆盖品类有限

1.2 问题定义（Problem Statement）

校园内存在高频、周期性的闲置物品流转需求，但现有渠道普遍存在信息不可检索、买卖双方身份不可信、商品信息描述成本高、交易履约依赖校外物流四大问题，导致校园二手交易撮合效率低下、成交率低。

1.3 产品机会点

  1. 地理闭环：所有用户同属一个校区，"线下面交"可行且成本最低 → 交易设计应围绕自提而非快递。
  2. 身份闭环：用户以学号注册，天然具备校园身份属性 → 可建立比陌生人平台更高的信任基线。
  3. 发布门槛：学生发布二手物品时最不愿写标题和描述 → 引入 AI 图像识别自动填充商品信息，显著降低发布成本（本产品名中"智能"的来源）。
  4. 品类集中：校园二手高度集中在教材、数码、宿舍用品、代步车等少数品类 → 分类体系可精简，无需大而全的电商分类树。

2. 产品定位与目标

2.1 产品定位（一句话）

面向单一高校校区学生的 C2C 二手闲置交易平台，以"AI 一键发布 + 校内自提"为核心，提供从发布、浏览、沟通到线下履约的轻量交易闭环。

2.2 产品边界

产品做（In Scope）

  • 商品发布（含 AI 智能识别辅助）、浏览、搜索、分类筛选、排序
  • 买卖双方一对一私聊（商品维度会话）
  • 购物车、收藏、订单流转、线下自提履约
  • 基于浏览/搜索行为的个性化推荐
  • 校园社区（帖子 + 评论）
  • 管理员后台基础数据管理

产品不做（Out of Scope）

  • 不介入资金流：无在线支付、无钱包、无平台担保交易。付款动作在系统中仅做状态标记，实际资金由买卖双方面付。
  • 不做物流配送：无快递、无运费模板，统一为线下自提。
  • 不做跨校 / 跨城交易：用户范围限定单一校区。
  • 不做售后维权体系：无退款、退货、申诉、仲裁流程。

关键产品决策说明 平台选择"信息撮合 + 线下自提"而非"在线支付 + 担保交易"，是刻意的轻量化取舍： 校内面交场景下，买家可当场验货，天然规避远程交易的信息不对称问题； 同时规避支付牌照、资金结算、纠纷仲裁等合规与研发成本。 该决策的代价是平台对交易的掌控力较弱，需通过信用积分、实名认证、评价体系等软性机制补偿。

2.3 产品目标（可度量）

目标维度 指标 目标值 度量方式
发布效率 单件商品平均发布耗时 ≤ 60 秒（使用 AI 识别时 ≤ 30 秒） 埋点计时
发布效率 AI 识别信息采纳率 ≥ 60%（用户未大幅修改识别结果即提交） 提交时对比识别值与最终值
撮合效率 商品发布到产生首个咨询的时长 ≤ 24 小时 首次消息时间 − 商品创建时间
撮合效率 商品成交率（完成订单 / 上架商品） ≥ 25% 订单与商品统计
活跃度 日活用户（DAU）占注册用户比 ≥ 15% 登录统计
内容供给 人均在架商品数 ≥ 1.5 件 商品统计

3.2 用户画像

画像 A：毕业季甩卖的学长（供给方主力）

  • 身份：大四学生，6 月毕业
  • 痛点：带不走的东西多（自行车、台灯、教材、小家电），时间紧，嫌拍照写描述麻烦
  • 诉求：批量、快速发布；希望一口价尽快出掉，不想反复议价
  • 关键需求：AI 识别一键填充、自提地址固定几个点、商品可一键下架

画像 B：开学季省钱的新生（需求方主力）

  • 身份：大一新生，9 月入学
  • 痛点：教材、宿舍用品全新购买贵；不了解校内行情；担心被坑
  • 诉求：低价、可信、就在校内；想先看货再决定
  • 关键需求：分类浏览、价格排序、卖家信用/实名标识、私聊议价、收藏比价

画像 C：数码爱好者（高频双向用户）

  • 身份：大二/大三，频繁更换手机、显卡、平板
  • 痛点：数码产品价值高、成色描述专业度要求高、买家疑虑多
  • 诉求：精确描述成色；多图展示；充分沟通后成交
  • 关键需求：新旧程度五档细分、多图上传、商品详情完整字段、私聊

画像 D：校园社区活跃者（内容供给）

  • 身份：各年级，爱分享
  • 痛点：交易之外有交流需求（求购、经验分享）
  • 诉求：有个能发帖讨论的地方
  • 关键需求：社区发帖、评论互动

4. 核心使用场景与用户故事

4.1 场景一：毕业季快速甩卖（供给主场景）

用户故事

作为一个即将毕业的大四学生，我希望拍张照片就能自动填好商品信息，这样我能在半小时内把十几件东西全部挂出去，而不是一个个敲字。

流程

  1. 用户在发布页上传商品照片
  2. 系统自动识别图片内容，返回：商品名称、建议分类、建议价格区间、生成描述
  3. 用户确认/微调后，选择自提地址、成色、价格
  4. 提交发布 → 商品上架，对全校可见

验收要点：AI 识别结果应可直接采纳，用户仅需补充价格与成色。

4.2 场景二：开学季淘教材（需求主场景）

用户故事

作为大一新生，我希望能按分类找到本学期的二手教材，并按价格从低到高排序，这样我不用在几百条群消息里翻找。

流程

  1. 首页选择"书籍资料"分类
  2. 输入课程名/教材名关键词搜索
  3. 按价格升序排序，浏览结果
  4. 对候选商品收藏（比价）或直接联系卖家
  5. 私聊确认库存与自提地点 → 下单 → 线下面交

4.3 场景三：高价值数码交易（信任敏感场景）

用户故事

作为想买二手笔记本的学生，我希望在下单前能和卖家充分沟通、看到尽可能多的实物图，因为几千块的交易我不能只看一张图就决定。

流程

  1. 商品详情页查看多图、成色描述、原价/现价对比、卖家信息
  2. 点击"联系卖家"进入商品维度会话
  3. 私聊议价、索取更多实拍图
  4. 达成一致 → 加入购物车/立即购买 → 创建订单
  5. 线下自提当场验货 → 确认收货

4.4 场景四：卖家管理在售商品（履约场景）

用户故事

作为卖家，我希望能看到所有与我相关的订单并按状态分类，这样我知道哪些要催付款、哪些要准备交付。

流程

  1. 订单页查看"我买到的 / 我卖出的"订单列表
  2. 按状态筛选（待付款/待自提/已完成/已取消）
  3. 待自提订单：线下交付后等待买家确认
  4. 商品售罄后系统自动标记为"已售出"

6. 功能需求详述

6.1 用户与认证模块

FR-U-01 学号注册 P0

需求描述 新用户通过学号完成注册，学号作为校内身份的唯一凭证。

输入字段与规则

字段 必填 规则
学号 student_id 是 唯一，长度 ≤ 32，全库唯一索引
用户名 username 是 长度 ≤ 64，展示用昵称
密码 password 是 后端加密存储（BCrypt），不明文返回
邮箱 email 否 唯一（若填写），格式校验
手机号 phone 否 ≤ 16 位

业务规则 - RU-1：学号不可重复注册 - RU-2：注册成功后默认赋予普通用户角色、正常状态 - RU-3：注册成功后默认信用积分 100 分 - RU-4：注册成功后默认未实名认证（is_verified = 0）

异常场景

场景 处理
学号已存在 提示"该学号已注册"，阻止提交
邮箱已存在 提示"邮箱已被使用"
必填项为空 前端表单校验拦截

FR-U-02 登录与身份保持 P0

FR-G-11 重复发布检测 P2 · V1.2

6.3 交易履约模块

FR-O-01 订单创建 P0

需求描述 买家对商品下单，生成待付款订单。

业务规则 - RU-1：下单前校验库存，库存不足时提示"库存不足，当前库存：X 件" - RU-2：订单创建后状态为"待付款" - RU-3：订单号全局唯一（时间戳 + 随机序列） - RU-4：冗余保存自提地址快照，避免商品地址变更后订单地址丢失 - RU-5：下单即预占库存（扣减），防止超卖；超时未付或主动取消则释放

待确认项 V1.0 订单结构为"一单一品"。若后续支持购物车批量下单，需引入订单明细表。

FR-O-02 订单支付 P0

需求描述 买家完成付款，订单进入"待自提"。

业务规则 - RU-1：仅"待付款"状态订单可执行支付 - RU-2：支付成功后订单状态置为"待自提"，记录付款时间 - RU-3：库存已在下单时预占，支付动作不重复扣减 - RU-4：若库存扣减后为 0，商品自动置为"已售出" - RU-5：V1.0 采用线下支付方式，平台不介入资金流，付款在系统中仅作状态标记；实际资金由买卖双方面付

升级路径 在线支付接入（FR-O-08，V2.0）需配套资金托管、退款、对账能力，属重大范围变更，需重新评估产品边界。

FR-O-03 订单取消与库存回滚 P0

需求描述 买家在付款前可取消订单，系统释放被预占的库存。

业务规则 - RU-1：仅"待付款"状态订单可取消 - RU-2：取消后订单状态置为"已取消"，记录取消时间与取消原因 - RU-3：取消时回滚库存 - RU-4：库存回滚后若商品原为"已售出"状态且库存 > 0，自动恢复为"已上架"

FR-O-04 订单确认收货 P0

需求描述 买家线下自提验货后确认收货，订单完成。

业务规则 - RU-1：仅"待自提"状态订单可确认收货 - RU-2：确认后订单状态置为"已完成"，记录完成时间

FR-O-05 / FR-O-06 订单列表与删除 P0/P1

需求描述 用户查看与自己相关的订单（买到的 / 卖出的），并可删除已完成或已取消的订单。

业务规则 - RU-1：订单列表同时包含"我作为买家"和"我作为卖家"的订单 - RU-2：订单列表冗余返回商品信息（标题、封面、价格）便于展示 - RU-3：仅"已完成"或"已取消"状态订单可删除，进行中订单不可删除 - RU-4：订单删除采用软删除，保留交易凭证用于后续对账与纠纷追溯

FR-O-07 交易超时自动处理 P1 · V1.2

需求描述 通过定时任务自动处理超时订单，避免订单长期悬挂占用库存。

规则设计

超时类型 触发条件 自动处理

11.2 范围界定原则

需求评审时的取舍依据：

  1. 能线下解决的，不做线上 —— 支付、物流、售后全部线下化，平台只做信息撮合
  2. 能用第三方能力的，不自研 —— AI 识别调用第三方 API，不训练自有模型
  3. 能后置的校验，先不上 —— 审核、风控在用户量起来后再补，先用信用积分过渡
  4. 单校区做深，不跨校做广 —— 地理密度决定撮合效率
