1. 项目背景与问题定义

1.1 业务背景

高校学生与初级求职者在技能成长过程中，普遍面临"学、练、评、面"四个环节彼此割裂的问题：课程平台只管看视频，刷题平台只管判对错，求职平台只管投简历，模拟面试则完全依赖学长学姐的人情帮忙。

目前（系统立项前）的现实形态：

现有渠道 具体问题
通用在线课程平台（慕课、B 站等） 内容海量但缺乏路径规划，学习者不知道"下一步学什么"；看完视频无闭环练习
编程刷题平台 有判题能力，但只判代码对错，不评价表达、逻辑与项目叙述能力
真人模拟面试 质量最高，但依赖人脉、不可重复、无法量化，多数学生一次都用不上
简历制作工具 解决排版问题，不解决"写什么"的问题；内容仍需用户自己憋
线下培训班 成本高、时间固定，且结课后即失去练习环境

1.2 问题定义（Problem Statement）

学习者从"开始学一门技能"到"通过面试拿到机会"之间，缺少一个能把学习、练习、反馈、模拟面试串成闭环的产品：学习环节缺少个性化路径，练习环节缺少及时反馈，面试环节缺少可反复练习、可量化评估的低成本环境。

本产品的机会点在于：用大模型把原本只有真人才能提供的"追问、评分、写反馈"这三件事自动化、可重复化、低成本化，从而让每个学生都能随时进行一次有质量的模拟面试。

1.3 立项目标

目标类型 目标描述 可衡量指标
业务目标 建立"学—练—评—面"一体化闭环，而非单点工具 用户在同一账号内完成课程学习、作业练习、模拟面试三类行为
差异化目标 AI 模拟面试可作为独立卖点拉取新用户 面试会话创建量、报告查看率
留存目标 通过等级、经验、成就、连续学习天数提升回访 连续学习天数、等级分布
效率目标 用 AI 替代重复性批改与评估工作 AI 批改覆盖率、教师人工批改占比

2. 产品定位与目标

2.1 产品定位

SmartEdu 是一款面向高校学生与初级求职者的智能教育平台，以"AI 模拟面试"为核心差异化，串联课程学习、作业练习、学习路径规划与简历生成，形成学、练、评、面的一体化成长闭环。

一句话概括：不只让你学完，还让你练过、被评过、面过。

2.2 产品边界

做什么（In Scope）

  • 课程内容的组织与展示（分类 → 课程 → 章节 → 小节 → 视频）
  • 学习进度跟踪与学习数据统计
  • 作业发布、提交与批改（AI 批改 + 教师批改双轨）
  • AI 生成个性化学习路径与节点跟进
  • AI 模拟面试（多面试官人设、多轮追问、自动评分、评估报告）
  • AI 简历生成与 DOCX 导出
  • AI 学习助手问答
  • 用户等级、经验、成就等成长激励体系
  • 后台管理（RBAC 权限、用户/课程/学生管理、数据统计）

不做什么（Out of Scope）

边界项 说明
支付与交易 order 表已设计，但无支付网关对接、无购物车、无结算流程
内容生产 不提供视频录制/剪辑/转码，课程视频依赖外部 URL 引用
多租户 SaaS 单租户部署；tenant 表为架构预留，本期不启用
直播与实时课堂 无 WebSocket 教室、无白板、无连麦
社交与社区 无论坛、无评论互动、无学习小组（课程评价仅为单向展示）
移动端原生应用 仅响应式 Web，无 iOS / Android 原生壳

2.3 核心价值主张

价值点 面向用户 实现支撑
随时随地的模拟面试 求职者 多面试官人设 + 大模型多轮追问 + 五维评分报告
AI 代替重复批改 学习者、教师 作业 AI 批改（按评分标准自动打分与反馈）
知道自己该学什么 初学者 AI 按目标技能生成学习路径，拆解为节点并跟进
成长看得见 全体用户 等级、经验、成就、连续天数、学习仪表盘
简历不用憋 求职者 一句话提示词生成结构化简历，支持 DOCX 导出

3. 目标用户与角色定义

3.1 角色清单

系统实际定义了两套完全隔离的账号体系：

角色 账号表 认证方式 入口 说明
学生 / 学习者 user（role=user） JWT（/api/auth/login） /login 平台 C 端主用户
教师 user（role=teacher） JWT（同上） /login 模型层已定义，业务上暂无专属功能入口
平台管理员 admin_user JWT（/api/admin/login，token 带 type=admin） /admin/login 后台管理，独立于 C 端账号

设计说明：后台管理员（admin_user）与 C 端用户（user）分表存储、独立登录、独立 Token 签发，二者不共用账号数据。管理员登录后的 Token 中带 type: "admin" 声明用于区分。

3.2 用户画像

画像一：在校生 · 小林（主要用户） - 大三计算机专业，自学前端，目标是暑期实习 - 痛点：课看了不少，但说不清自己会什么；投简历前没人帮着模拟面试 - 使用路径：注册 → 浏览课程 → 按学习路径推进 → 做作业 → AI 模拟面试 → 生成简历 - 关注点：路径是否清晰、反馈是否及时、面试报告是否具体

画像二：求职者 · 阿杰（核心用户） - 应届生，技术尚可但表达紧张，面试一问深就卡壳 - 痛点：找不到真人模拟面试，自己练没有反馈 - 使用路径：直接进入 AI 面试 → 选择面试官 → 多轮答题 → 看报告 → 针对性重练 - 关注点：追问是否真实、评分维度是否全面、报告能否指出具体问题

画像三：平台运营 · 管理员 - 负责课程上架、学生账号管理、查看平台数据 - 使用路径：后台登录 → 课程管理 → 学生管理 → 首页看统计 - 关注点：操作效率、数据准确性、权限是否可控

4. 核心使用场景与用户故事

4.1 场景一：从零开始学一项技能（学习闭环）

用户故事

作为一个自学前端的学生，我希望输入想学的技能后系统能帮我规划出一条路径，这样我就不用自己纠结先看什么。

流程 1. 注册/登录 → 进入"学习路径"页 2. 输入目标技能、当前水平、每日可投入时间 3. 系统调用 AI 生成路径，拆解为若干节点（课程 / 练习 / 项目 / 测评） 4. 用户按"今日任务"逐节点推进，可标记完成或跳过 5. 节点完成后自动更新路径整体状态与进度

验收要点 - 路径生成失败时用户应明确感知，而不是拿到一条看起来正常的模板路径 - 节点与站内课程应建立可点击的跳转关联

4.2 场景二：AI 模拟面试（核心场景）

用户故事

作为一个即将面试的求职者，我希望和 AI 面试官进行多轮真实追问，并在结束后拿到一份能指出具体问题的评估报告，这样我能知道该练什么。

流程 1. 进入"AI 面试" → 从面试官列表中选择一位（不同人设对应不同岗位/难度/风格） 2. 选择岗位、面试类型、难度 → 创建会话 3. 进入面试页：AI 提出开场问题 → 用户作答（文字输入 / 语音输入） 4. AI 基于上下文追问（系统保留最近 20 条对话作为上下文窗口） 5. 每轮作答实时落库为一条问答记录，并按五维打分 6. 用户点击"结束面试" → 系统汇总生成面试报告 7. 报告页展示综合评分、五维雷达、优点/不足/建议、逐轮对话回放

验收要点 - AI 追问应基于用户上一轮回答内容，而非固定话术 - 面试中断/刷新后应能恢复会话与历史对话 - 报告中的评分应来自 AI 真实评估，失败时须明确标注"评估失败"而非给默认值

4.3 场景三：作业提交与 AI 批改

用户故事

作为一个学完课程的学生，我希望提交作业后能立刻拿到分数和反馈，而不是等老师批改。

流程 1. 进入"作业中心" → 查看作业列表（区分课程、截止时间） 2. 进入作业详情 → 查看题目要求与评分标准 3. 提交答案（文本 / 附件） 4. 系统触发 AI 批改：按评分标准打分并生成反馈，status 置为"AI 已批改" 5. 教师可查看并人工复核，给出最终分数（status 置为"教师已批改"） 6. 教师可发起"重新批改"

验收要点 - AI 批改失败时必须明确提示失败并引导重试，不得给出任何近似分数或默认分数

4.4 场景四：AI 简历生成与导出

用户故事

作为一个要投简历的学生，我希望用一句话描述自己的背景，就能生成一份结构化的简历并导出 Word 继续编辑。

流程 1. 进入"AI 简历" → 输入提示词（目标岗位、经历描述） 2. 系统生成结构化简历 JSON（基本信息/技能/经历/项目/教育/证书） 3. 页面内可编辑各字段 4. 点击导出 → 生成 DOCX 文件下载

验收要点 - AI 生成内容必须是基于用户输入的提炼，而非模型编造（当前 Prompt 允许模型"推断合理细节"，存在简历造假风险）

4.5 场景五：管理员内容运营

用户故事

作为平台运营，我希望能在后台完成课程上架、学生账号管理与数据查看，且不同管理员权限可控。

流程 1. 后台登录 → 首页查看平台统计（用户数、课程数、作业数等）与最近登录记录 2. 课程管理：新增/编辑/上下架课程 3. 学生管理：查看列表、编辑资料、重置密码 4. 系统管理：管理员账号 CRUD、角色配置、菜单配置

验收要点 - 角色与菜单权限配置应真实生效于接口层（当前仅作用于后台菜单展示，接口层未消费）

6.5 AI 模拟面试 ★ 核心模块

6.5.1 面试官人设

每位面试官包含：姓名、头像、岗位、公司、专长、难度等级、面试风格、性格特征，并可独立配置 AI 服务参数（API Key、Base URL），支持不同面试官接入不同的模型服务。

面试官在页面上的形象、标题与开场白由人设展示配置控制，与面试官基础数据分离维护，便于运营调整而不影响会话数据。

6.5.2 会话与对话

规则 取值
会话状态 ongoing / completed / abandoned
面试类型 技术面 / 行为面 / 系统设计 等
难度 easy / medium / hard
上下文窗口 保留最近 20 条对话作为上下文
对话存储 逐条落 interview_dialogue，按 sequence 排序
单题记录 每条问答落 interview_qa_record，含答题耗时

6.5.3 评分体系

单题评分（每轮作答后立即执行）

返回字段：score（0-100）、feedback、technical_accuracy、logic_clarity、expression_completeness

综合评估（面试结束时执行）

五个维度：overall（综合）、technical（技术能力）、communication（沟通表达）、logic（逻辑思维）、problem_solving（问题解决）

同时返回 strengths（优点）、weaknesses（不足）、suggestions（改进建议）

报告生成规则

综合得分 = 所有单题 AI 得分的算术平均（整除）
评级阈值：≥ 80 记为"表现优秀"；< 60 记为"存在薄弱环节"

评分规则约束（强制）：五个维度必须由 AI 独立评估，不得复用同一平均分（否则雷达图将失去区分度）；评估失败时须明确提示，严禁返回任何默认分数。

6.5.4 AI 服务降级策略

环节 AI 服务失败时的处理要求
追问生成 提示"AI 服务暂时不可用，请稍后重试"，中断本轮作答
单题评分 标记该题"评分失败"，该轮不纳入报告统计，提示用户可重答
综合评估 明确提示"评估失败"，不生成报告，提供重试入口

设计原则：AI 能力可以降级，但降级必须对用户可见。静默降级会让用户对系统给出的评价产生错误信任，在教育类产品中是原则性问题。
